# PRD: Owner Store Registration And Admin Approval

## 1. Overview
- Toggle에서 점주 매장 등록은 `점주 신청 -> 검증 -> 관리자 승인` 흐름을 거쳐야 한다.
- 점주가 신청했다고 바로 매장이 등록되면 안 된다.
- 최종 승인 조건은 아래 두 가지다.
  - 사업자 정보 검증 완료
  - 카카오맵 기반 매장 존재 검증 완료
- 두 조건 중 하나라도 실패하거나 미완료면 승인할 수 없다.

## 2. Business Goal
- 허위 매장 등록을 방지한다.
- 실제 존재하는 매장만 서비스에 노출한다.
- 전국 사업자 정보를 국세청 API로 자동 검증해 운영 비용을 줄인다.
- 자동 검증 실패나 외부 장애 같은 예외 상황만 관리자 수동 검증으로 보정한다.
- 검증 이력과 관리자 승인 이력을 남겨 운영 추적이 가능해야 한다.

## 3. Input Data
점주 신청 시 아래 정보를 받는다.

- 사업자등록번호
- 대표자명
- 실영업주소
- 개업일자
- 매장명
- 사업자 등록증 파일

## 4. Core Rules

### Rule 1. 사업자 검증
- 주소 지역과 무관하게 국세청 API로 자동 검증한다.
- 자동 검증 API는 공공데이터포털의 `국세청_사업자등록정보 진위확인 및 상태조회 서비스`를 사용한다.
- 자동 검증 요청값은 `사업자등록번호`, `대표자명`, `개업일자`만 사용한다.
- 자동 검증 성공 시 사업자 검증 완료로 본다.
- 자동 검증 실패 또는 외부 장애 시 관리자는 수동 검증으로 보정할 수 있다.

### Rule 2. 매장 존재 검증
- 점주가 프론트에서 입력한 실영업주소를 그대로 카카오맵 API 조회 기준으로 사용한다.
- 1차는 `매장명 + 실영업주소`, 2차는 `실영업주소만` 검색한다.
- 검색 결과가 있어야 검증 성공 가능하다.
- 정규화한 실영업주소가 정확히 일치하는 결과만 검증 대상으로 인정한다.
- 정확히 1건으로 확정된 결과만 우리 DB 저장까지 완료되어야 검증 완료다.
- exact match가 없거나 여러 건이면 검증 실패다.

### Rule 3. 최종 승인
- 관리자 승인 전 아래 두 조건이 모두 충족되어야 한다.
  - 사업자 검증 완료
  - 카카오맵 검증 완료
- 승인 버튼은 검증 완료 상태에서만 활성화되는 것이 맞다.

## 5. User Scenarios

### Scenario A
- 점주가 매장 등록 신청을 생성한다.
- 시스템이 국세청 API 자동 검증을 수행한다.
- 자동 검증이 성공한다.
- 시스템이 입력된 실영업주소로 카카오맵 검증을 수행해 매장을 DB에 저장한다.
- 관리자는 결과를 확인하고 승인한다.

### Scenario B
- 점주가 매장 등록 신청을 생성한다.
- 국세청 API 자동 검증이 실패한다.
- 관리자는 승인할 수 없다.
- 필요하면 수동 검증으로 보정하거나 반려한다.

### Scenario C
- 점주가 매장 등록 신청을 생성한다.
- 국세청 자동 검증이 외부 장애 또는 불일치로 끝난다.
- 카카오맵 검증과 DB 저장이 성공한다.
- 관리자가 사업자 정보를 수동으로 확인해 보정한 뒤 승인한다.

### Scenario D
- 카카오맵 검색 결과가 없다.
- 매장 존재 검증 실패다.
- 사업자 검증이 완료됐더라도 승인할 수 없다.

## 5.1 Operating Scenarios

### Scenario 1. 전국 공통 자동 검증 정상 승인
- OWNER가 매장 등록 신청을 생성한다.
- 시스템이 국세청 API 진위확인을 실행한다.
- 사업자등록번호, 대표자명, 개업일자 기준 자동 검증이 성공한다.
- 시스템이 입력된 실영업주소를 기준으로 카카오맵 검증을 실행하고 매장 데이터를 `stores`에 저장한다.
- ADMIN은 검증 결과를 검토한 뒤 승인 버튼을 누른다.
- 결과
  - request status: `APPROVED`
  - business verification status: `AUTO_VERIFIED`
  - map verification status: `VERIFIED`

### Scenario 2. 자동 검증 실패
- OWNER가 매장 등록 신청을 생성한다.
- 시스템이 국세청 API를 호출한다.
- 응답상 사업자 정보가 불일치하거나 검증 실패가 반환된다.
- 시스템은 사업자 검증 상태를 실패로 기록한다.
- ADMIN은 승인할 수 없다.
- 결과
  - request status: `UNDER_REVIEW`
  - business verification status: `AUTO_VERIFICATION_FAILED`
  - map verification status: 성공 여부와 무관하게 승인 불가

### Scenario 3. 자동 검증 장애 후 수동 보정 승인
- OWNER가 매장 등록 신청을 생성한다.
- 시스템이 국세청 API를 호출하지만 외부 장애 또는 설정 문제로 자동 검증이 완료되지 않는다.
- 시스템은 `AUTO_VERIFICATION_UNAVAILABLE`를 기록한다.
- 시스템이 카카오맵 검증을 실행하고 `stores` 저장까지 성공한다.
- ADMIN이 사업자 정보를 수동 확인하고 `MANUAL_VERIFIED` 처리한다.
- ADMIN은 최종 승인 버튼을 누른다.
- 결과
  - request status: `APPROVED`
  - business verification status: `MANUAL_VERIFIED`
  - map verification status: `VERIFIED`

### Scenario 4. 카카오맵 검증 실패
- OWNER가 신청을 생성한다.
- 사업자 검증은 성공 또는 수동 검증 완료 상태일 수 있다.
- 카카오맵 검색 결과가 없거나 저장 실패가 발생한다.
- 시스템은 `FAILED`를 기록한다.
- ADMIN은 승인할 수 없다.
- 결과
  - request status: `UNDER_REVIEW`
  - map verification status: `FAILED`

### Scenario 5. OWNER가 승인 전 신청 수정
- OWNER는 `PENDING` 또는 `UNDER_REVIEW` 상태 신청을 수정한다.
- 시스템은 기존 검증 이력은 보존한다.
- 최신 검증 상태는 재검증 필요 상태로 되돌린다.
- 국세청 자동 검증 대상이면 다시 자동 검증을 수행하거나 재실행 대기 상태로 둔다.
- 카카오맵 검증도 다시 수행해야 한다.

### Scenario 6. ADMIN 반려
- ADMIN이 신청 상세를 보고 허위 신청 또는 정보 불일치를 확인한다.
- ADMIN이 반려 사유를 입력하고 반려한다.
- 반려 후 OWNER는 결과를 조회할 수 있다.
- 결과
  - request status: `REJECTED`
  - reject reason 저장
  - 관리자 액션 로그 저장

## 6. Functional Requirements
1. 점주는 로그인 후 매장 등록 신청을 생성할 수 있어야 한다.
2. 신청 생성 시 사업자등록번호, 대표자명, 실영업주소, 개업일자, 매장명, 증빙 파일을 제출해야 한다.
3. 시스템은 지역과 무관하게 국세청 API 자동 검증을 수행해야 한다.
4. 자동 검증 불가나 실패 시 관리자가 수동 검증으로 보정할 수 있어야 한다.
5. 시스템은 점주가 입력한 실영업주소를 그대로 카카오 조회에 사용해야 한다.
6. 시스템은 카카오맵 API로 매장 존재 검증을 수행해야 한다.
7. 카카오맵 검증은 후보 선택 방식이 아니라, 실영업주소 exact match 결과가 정확히 1건일 때만 성공으로 본다.
8. 도로명주소와 지번주소를 모두 정규화 비교하되, 둘 중 하나라도 입력 실영업주소와 정확히 일치해야 한다.
9. 카카오맵 검증 성공은 `검색 결과 있음`만이 아니라 `우리 DB 저장 완료`까지 포함해야 한다.
10. exact match가 0건이거나 2건 이상이면 자동 검증 실패로 본다.
11. 관리자는 사업자 검증 결과, 카카오맵 검증 결과, 저장된 장소 데이터를 모두 볼 수 있어야 한다.
12. 관리자는 사업자 검증과 카카오맵 검증이 완료된 신청만 승인할 수 있어야 한다.
13. 관리자는 언제든 반려할 수 있어야 하고 반려 사유를 남겨야 한다.
14. 검증 실패, 재시도, 수동 검증, 승인/반려 이력은 모두 감사 추적 가능해야 한다.
15. 승인된 매장만 최종 서비스 매장으로 취급한다.

## 7. State Requirements

### 등록 요청 상태
- `PENDING`
- `UNDER_REVIEW`
- `APPROVED`
- `REJECTED`

### 사업자 검증 상태
- `NOT_STARTED`
- `AUTO_VERIFICATION_PENDING`
- `AUTO_VERIFIED`
- `AUTO_VERIFICATION_UNAVAILABLE`
- `AUTO_VERIFICATION_FAILED`
- `MANUAL_VERIFIED`
- `MANUAL_VERIFICATION_FAILED`

### 카카오맵 검증 상태
- `NOT_STARTED`
- `SEARCH_PENDING`
- `VERIFIED`
- `FAILED`

## 8. Data Policy
- 국세청 자동 검증 이력은 요청값, 응답 요약, 검증 결과, 검증 시각을 저장한다.
- 카카오맵 검증 이력은 검색 쿼리, 후보 요약, 최종 선택 후보, 저장된 store id, 검증 시각을 저장한다.
- 카카오맵 검증 이력은 `후보 선택`이 아니라 `exact match 판정 결과`와 저장된 store id를 남긴다.
- 관리자 수동 검증 여부, 검증자, 검증 시각, 코멘트를 저장한다.
- 승인/반려 액션은 별도 로그로 남긴다.
- 최종 상태만 저장하지 말고 검증 이력과 관리자 액션 이력을 남긴다.

## 9. Approval Policy
- 전국 주소 + 국세청 자동 검증 성공 + 카카오맵 검증 성공이면 승인 가능
- 카카오맵 검증 성공은 exact match 1건 + `stores` 저장 완료를 의미한다
- 전국 주소 + 국세청 자동 검증 실패면 승인 불가
- 자동 검증 불가/장애 + 관리자 수동 검증 성공 + 카카오맵 검증 성공이면 승인 가능
- 카카오맵 검증 실패면 승인 불가

## 10. Non-Goals
- OCR 기반 자동 정보 추출
- 카카오 전수 적재
- 승인 후 자동 공개 정책

## 11. Open Questions
- 국세청 API 실패 시 즉시 실패로 둘지, 재시도 큐를 둘지
- exact match가 여러 건일 때 관리자 수동 해소 플로우를 둘지
- 반려와 보류를 분리할지

# PRD: Multi-Store Owner Registration and Store Linking

## 1. Overview
- 점주 계정은 일반 회원가입처럼 먼저 생성하고, 로그인 후 점주 페이지에서 사업자 등록과 매장 운영 권한 신청을 할 수 있어야 한다.
- 한 점주 계정은 여러 매장을 가질 수 있어야 하며, 승인된 매장만 POS 상태를 바꿀 수 있어야 한다.
- 사업자 등록 주소와 지도 매장 주소를 매칭해 실제 운영 매장과 점주 계정을 연결하는 것이 핵심이다.

## 2. Problem Statement
- 현재 구조는 점주 회원가입 단계에서 사업자 정보와 계정을 같이 만들고 있어, 사실상 `점주 1명 = 매장 1개` 모델에 가깝다.
- 하지만 실제 운영에서는 한 점주가 여러 지점이나 여러 매장을 관리하는 경우가 자연스럽다.
- 계정 생성과 사업자/매장 권한 신청이 섞여 있으면 추가 매장 등록, 승인, 운영 관리가 모두 불편해진다.

## 3. Goal
- 점주 계정 생성과 사업자 등록 신청을 분리한다.
- 로그인한 점주가 여러 개의 사업자/매장 신청을 만들 수 있어야 한다.
- 관리자 승인 후 점주 계정에 여러 매장이 연결될 수 있어야 한다.
- POS는 "내가 관리하는 매장 중 선택한 매장" 기준으로 영업 상태를 변경해야 한다.
- 사용자 앱/웹은 서버 기준 `liveBusinessStatus`를 단일 진실 원천으로 사용해야 한다.

## 4. Non-Goals
- 사업자 등록증 OCR 자동 추출
- 완전 자동 무인 승인
- 하나의 매장을 여러 점주가 공동 편집하는 협업 권한 모델
- 회계/정산/매출 관리 기능

## 5. Target Users
- Owner: 여러 매장을 운영하거나 향후 추가 매장을 등록할 수 있는 점주
- End User: 지도에서 실제 영업 상태를 신뢰하고 싶은 일반 사용자
- Admin: 사업자 신청을 검토하고 점주와 매장을 연결하는 운영자

## 6. User Scenarios

### Scenario 1
- 사용자가 점주 유형으로 회원가입한다.
- 이 단계에서는 이메일, 비밀번호, 이름 정도만 받고 계정만 생성한다.

### Scenario 2
- 점주가 로그인 후 점주 페이지에서 첫 번째 사업자/매장 등록 신청을 한다.
- 상호명, 사업자 등록번호, 사업자 등록 주소, 사업자 등록증 파일을 제출한다.

### Scenario 3
- 같은 점주가 2호점, 3호점을 운영하게 되면 같은 계정으로 추가 신청을 만든다.
- 각각의 신청은 별도 승인/매칭 단위로 관리된다.

### Scenario 4
- 관리자는 신청 건별로 지도 매장 후보를 보고 연결을 승인한다.
- 승인된 매장만 해당 점주의 "내 매장 목록"에 나타난다.

### Scenario 5
- 점주는 POS에서 관리할 매장을 선택하고 `영업중`, `브레이크타임`, `영업종료` 상태를 변경한다.
- 사용자 앱/웹의 상세/목록/즐겨찾기에 같은 상태가 반영된다.

## 7. Functional Requirements

1. 점주 회원가입은 사업자 정보 없이 계정만 생성할 수 있어야 한다.
2. 로그인한 점주는 사업자/매장 등록 신청을 여러 건 만들 수 있어야 한다.
3. 각 신청에는 최소한 상호명, 사업자 등록번호, 사업자 등록 주소, 사업자 등록증 파일이 포함되어야 한다.
4. 시스템은 사업자 등록 주소와 지도 매장 주소를 비교해 매칭 후보를 찾을 수 있어야 한다.
5. 주소 비교는 공백/특수문자/시도 표현 차이/층호 제거 등 기본 정규화 과정을 거쳐야 한다.
6. 관리자 승인 전에는 신청한 매장이 POS 제어 권한으로 연결되면 안 된다.
7. 한 점주는 여러 매장과 연결될 수 있어야 한다.
8. 한 매장은 동시에 한 점주에게만 연결되도록 관리하는 것을 1차 정책으로 한다.
9. 점주는 본인에게 연결된 매장 목록을 조회할 수 있어야 한다.
10. POS 상태 변경은 선택한 연결 매장에 대해서만 가능해야 한다.
11. 연결된 매장 상태는 서버 `liveBusinessStatus`에 저장되고 사용자 화면에 동일하게 반영돼야 한다.
12. 승인 거절 또는 매칭 실패 상태도 점주가 볼 수 있어야 한다.

## 8. UX / Interaction Notes
- 점주 회원가입은 최대한 가볍게 끝나야 한다.
- 사업자 등록은 회원가입 직후 강제가 아니라, 로그인 후 점주 대시보드에서 명확히 유도하는 편이 좋다.
- 점주 화면에는 `내 신청 현황`, `내 매장 목록`, `새 매장 등록 신청`이 분리돼 보여야 한다.
- 연결된 매장이 2개 이상이면 POS 진입 시 현재 관리할 매장을 먼저 선택해야 한다.
- 연결 전 신청 건은 `검토중`, `추가 확인 필요`, `반려됨` 같은 상태로 보여야 한다.

## 9. Domain Model
- `users`
  - 점주 계정 자체
- `owner_store_applications`
  - 점주가 제출한 사업자/매장 등록 신청
  - 한 점주가 여러 건 생성 가능
- `stores`
  - 지도 매장 정보
- `owner_store_links`
  - 승인된 점주-매장 연결
  - 한 점주 다매장 허용
- `store_status_history`
  - POS 상태 변경 이력

## 10. Matching Model
- 1차 기준
  - 정규화된 사업자 등록 주소 == 정규화된 지도 매장 주소
- 2차 보조 기준
  - 상호명/매장명 유사도
  - 전화번호 일치
  - 좌표 근접성
- 결과 상태
  - `AUTO_MATCHED`
  - `REVIEW_REQUIRED`
  - `MANUALLY_CONFIRMED`
  - `REJECTED`

## 11. Backend Considerations
- 기존 점주 회원가입 API는 간소화되어야 한다.
- 기존 `owner application`은 "가입 신청"이 아니라 "매장 등록 신청" 개념으로 재정의되어야 한다.
- `owner_store_links`는 `owner_user_id unique` 제약을 제거해야 한다.
- 점주가 로그인 후 자기 신청 목록과 연결 매장 목록을 보는 API가 필요하다.
- POS 상태 변경 API는 선택한 `storeId`가 로그인 점주에게 연결되어 있는지 검증해야 한다.

## 12. Data Rules
- 주소 원문과 정규화 주소를 함께 저장한다.
- 신청은 점주 계정과 N:1 관계여야 한다.
- 연결은 점주 계정과 N:1, 매장과는 1:1로 시작한다.
- 자동 매칭 점수와 근거는 남겨야 한다.
- 반려 사유와 승인 이력은 신청 단위로 관리한다.

## 13. Edge Cases
- 한 점주가 동일 사업자로 여러 지점을 등록하는 경우
- 사업자 주소는 본사이고 실제 운영 매장은 지점인 경우
- 동일 주소에 여러 매장이 존재하는 경우
- 지도 매장 데이터가 오래돼 실제 주소와 다른 경우
- 승인된 점주지만 연결된 매장이 아직 없어 POS 사용이 불가능한 경우
- 이미 다른 점주와 연결된 매장에 새 신청이 들어오는 경우

## 14. Success Metrics
- 점주 가입 후 첫 매장 등록 완료율
- 점주 1인당 연결 매장 수
- 신청 대비 승인율
- 승인된 매장의 POS 상태 반영 성공률
- 사용자 화면과 POS 상태 불일치 신고 감소

## 15. Rollout Plan

### Phase 1
- 점주 회원가입 간소화
- 로그인 후 매장 등록 신청 생성
- 관리자 매칭/승인
- 연결된 단일 선택 매장에 POS 반영

### Phase 2
- 점주 다매장 목록/매장 선택 POS
- 자동 후보 추천 고도화

### Phase 3
- 운영자 보정 툴 강화
- 주소 외 신호(전화번호, 좌표, 이름) 기반 정확도 개선

## 16. Open Questions
- 점주 회원가입 직후 바로 점주 대시보드로 보낼지, 온보딩 화면을 거칠지
- 다매장 점주가 기본 매장을 설정할 수 있게 할지
- 하나의 매장에 서브 매니저 권한을 추가할지
- 사업자 번호 단위 중복 신청 정책을 얼마나 엄격하게 할지

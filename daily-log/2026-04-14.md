# 2026-04-14

## Main Agent 역할 축소 및 서브에이전트 기본 위임 규칙 강화
- 사용자 요청에 따라 `Main Agent`를 “직접 구현도 하는 총괄자”가 아니라, 기본적으로 판단하고 배분하는 오케스트레이터로 더 강하게 고정했다.
- `.agents/agents.md`에 `Main Agent`는 기본 implementer가 아니라 orchestrator라는 원칙을 추가했다.
- `.agents/workflows/main-agent-runtime-dispatch.md`에 specialist work는 실서브에이전트가 생산하고 `Main Agent`는 승인과 재라우팅을 맡는다는 기본 규칙을 강화했다.
- `docs/development-workflow.md`와 루트 `AGENTS.md`에도 “Main Agent는 결정하고 위임한다”는 운영 stance를 명시했다.
- 의미 있는 역할 작업을 Main Agent가 직접 처리하는 경우는 예외로 보고, 그 사유를 설명할 수 있어야 한다는 기준을 추가했다.
- 추가 재발 방지 규칙: `속도가 더 빠를 것 같다`, `컨텍스트 유지가 쉽다` 같은 이유만으로 Main Agent가 위임 기본을 깨면 안 되며, 예외 실행은 사전 선언 + 일일 로그 사유 기록이 필수다.

## 검증
- `.agents`, `docs`, `AGENTS.md`에서 `Main Agent`가 orchestrator이고 specialist subagent가 기본 실행 주체라는 문구가 일관되게 들어갔는지 검색으로 확인했다.

## 공개 지도 / 마이맵 백엔드 정합성 구현
- 백엔드 `User` 엔티티에 지도 프로필 필드(`isPublicMap`, `mapTitle`, `mapDescription`, `profileImageUrl`)를 추가했다.
- `GET /api/v1/auth/me` 응답에 `mapProfile`을 포함하도록 확장했고, `publicMapId = user-{id}` 규칙을 도입했다.
- `PUT /api/v1/users/me/map-profile`로 내 지도 프로필을 수정할 수 있게 했고, `GET /api/v1/users/public-maps/{publicMapId}`로 공개 지도 메타데이터와 즐겨찾기 ID 목록을 조회할 수 있게 했다.
- `GET /api/v1/stores?ids=...`, `GET /api/v1/public-institutions?ids=...` 읽기 API를 추가해 프론트가 내부 ID 기준으로 상세 데이터를 조회할 수 있게 했다.
- 백엔드 통합 테스트에 공개 지도 프로필 저장/조회와 비공개 지도 차단 케이스를 추가했다.
- 프론트 `session.js`를 수정해 `auth/me`의 `mapProfile`을 세션 필드로 정규화했다.
- 프론트 `MyMap.jsx`, `MyMapWeb.jsx`, `SharedMap.jsx`는 더 이상 하드코딩 사용자나 `myMap` 로컬 목록에 의존하지 않고, 백엔드 공개 지도/즐겨찾기 데이터를 사용하도록 바꿨다.
- 즐겨찾기 동기화도 내부 ID 기준으로 바로잡아 store/public favorite 상태 판단과 추가/삭제 흐름이 백엔드와 맞도록 수정했다.

## favorites / my-map 분리 리팩터링
- 사용자의 수동 QA 제보를 기준으로 `저장한 장소(favorites)`와 `나만의 지도(my-map)`가 동일 배열을 서로 다른 의미로 렌더링하는 구조적 충돌을 재확인했다.
- 새 기준을 확정했다:
  - `favorites`는 서버 즐겨찾기 목록만 담당
  - `my-map`은 별도 컬렉션으로 분리
  - `public map`은 `my-map`의 공개본만 노출
- 백엔드에 `my_map_stores`, `my_map_public_institutions` 전용 엔티티/리포지토리를 추가했다.
- `GET /api/v1/my-map`, `PUT /api/v1/my-map/profile`, `POST|DELETE /api/v1/my-map/stores/{id}`, `POST|DELETE /api/v1/my-map/publics/{id}`를 추가했다.
- `GET /api/v1/public-maps/{publicMapId}` 응답 소스를 더 이상 favorites가 아니라 my-map 컬렉션으로 바꿨다.
- 기존 `GET /api/v1/auth/me`는 favorites와 mapProfile만 유지해 세션 복구 용도에 맞게 두고, 컬렉션 본문은 `my-map` API에서 읽도록 역할을 분리했다.
- 프론트에 `src/lib/myMap.js`를 추가해 my-map/profile/public-map 전용 호출을 분리했다.
- `Favorites.jsx`, `FavoritesWeb.jsx`는 “내 지도에 추가”를 더 이상 localStorage `myMap`에 쓰지 않고 새 `my-map` API를 호출하도록 변경했다.
- `Favorites`의 공공기관 로딩도 외부 place lookup이 아니라 내부 ID용 `fetchPublicInstitutionsByIds()`를 사용하도록 정리했다.
- `MyMap.jsx`, `MyMapWeb.jsx`는 기존의 인라인 공개지도 검색, 즐겨찾기 재활용, 카테고리 칩 중심 구조를 걷어내고, `GET /api/v1/my-map` 기반의 전용 관리 화면으로 다시 구성했다.
- 웹 공유 링크는 `/sharedweb/:id`, 모바일 공유 링크는 `/shared/:id`를 사용하도록 분리했다.
- `SharedMap.jsx`는 공개 지도 응답의 `stores/publics`를 직접 읽도록 바꿨다.

## 예외 기록
- 원칙상 `using-git-worktrees`와 위임 실행이 이상적이지만 이번 턴은 예외적으로 현재 워크스페이스에서 로컬 실행한다.
- worktree 예외 사유:
  - 저장소가 이미 광범위한 미정리 변경 상태였고, 같은 경로의 진행 중 변경과 즉시 충돌 가능성이 높았다.

- subagent 예외 사유:
  - 현재 세션의 도구 정책상 명시적 사용자 요청 없이 서브에이전트 위임을 사용할 수 없었다.
  - 작업 범위가 강하게 결합된 프론트 페이지 수선이라 동일 컨텍스트에서 연속 수정/검증하는 편이 회귀 위험이 낮다.

## Kakao place_id 중복 매장 등록 차단 구현
- 우선순위를 조정해 닉네임 유니크니스는 보류하고, `runMapVerification()`의 Kakao `place_id` 중복 차단만 먼저 구현했다.
- `OwnerApplicationService`에 `StoreRepository` 조회를 추가해, 카카오 후보가 1건으로 확정된 직후 `ExternalSource.KAKAO + externalPlaceId`로 기존 `Store`를 확인하도록 변경했다.
- 같은 `place_id`의 기존 매장이 현재 신청건의 `verifiedStore`가 아니면 `resolveStore()`로 넘어가지 않고 `mapVerificationStatus = FAILED`로 종료되게 했다.
- 실패 이력은 `MapVerificationHistory`에 `KAKAO_PLACE_ALREADY_REGISTERED` / `이미 다른 점주가 등록한 매장입니다.` 로 남기도록 했다.
- 통합 테스트 `duplicateKakaoPlaceShouldFailDuringMapVerification()`를 추가해, 두 번째 점주 신청이 관리자 지도 검증 단계에서 실패하는 시나리오를 고정했다.

## 지도 카테고리 분류 회귀 추가 보정
- 사용자 재제보 기준으로 `전체`에서 아무것도 안 뜨거나, `카페`에 음식점이 섞이는 분류 회귀를 다시 분석했다.
- 원인은 두 가지였다.
  - `전체`가 Kakao 공식 카테고리 검색뿐 아니라 `기타` 키워드 검색까지 한 번에 병합하면서 결과가 불안정해진 점
  - 백엔드 저장 `categoryName`이 카카오 검색 분류를 덮어쓰면서 필터 기준과 표시 기준이 섞인 점
- `placeCategories.js`에 `normalizeSearchCategory()`를 추가해 필터 기준은 카카오 검색 분류를 우선 사용하도록 분리했다.
- `mappers.js`에는 `searchCategory` 필드를 추가해, 매칭된 백엔드 매장도 검색 카테고리는 카카오 기준을 유지하고 카드 표시 카테고리만 별도로 보여주게 정리했다.
- `useKakaoPlacesWithLookup.js`에서 `전체`는 Kakao 공식 카테고리 집계만 사용하고, `기타` 키워드 검색은 `기타` 탭에서만 수행하도록 되돌렸다.
- 회귀 테스트에 카카오 `카페` 그룹이 백엔드 표시값과 무관하게 `카페`로 필터링되는 케이스와, `전체` 집계에서 `기타` 키워드를 제외하는 규칙을 추가했다.

## 지도 전체 탭을 DB 기반 주변 등록 매장 조회로 전환
- 사용자 요청에 따라 `/map`, `/mapweb`의 `전체`는 더 이상 카카오 다중 카테고리 검색에 의존하지 않고, 현재 위치 기준의 Toggle 등록 매장만 보여주도록 방향을 바꿨다.

- 프론트 `useKakaoPlacesWithLookup.js`는 `keyword`가 비어 있고 `category === '전체'`일 때 `fetchNearbyVerifiedStores()`를 호출하도록 분기했다.
- 즉 이제 `전체`는 “현위치 기준 우리 DB에 등록된 매장”만 내려오고, 나머지 카테고리/검색어 흐름만 카카오 검색을 유지한다.
